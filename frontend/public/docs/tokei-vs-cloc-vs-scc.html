tokei vs cloc vs scc: which line counter?

tokei, cloc, and scc are the three most popular open-source line counters, and all three split a local source tree into code, comment, and blank lines. The differences: tokei (Rust) is built for fast counting with compact output; cloc (Perl) is the oldest and has the widest language database plus a diff mode; scc (Go) adds cyclical complexity estimates, COCOMO effort projections, and license detection on top of the counts.

All three run on Linux, macOS, and Windows, and all three read a local checkout — none of them talks to a hosted repository by URL.

tokei

tokei is the counter to reach for when the job is "count this tree, fast, without ceremony." Output is a compact per-language table; --output json emits machine-readable totals via serde, and a tokei.toml can carry a shared configuration. It supports 200+ languages and is the engine OctoCounts runs server-side — the OctoCounts vs tokei page covers the split of labor between the CLI and the web service.

cloc

cloc has been counting trees since the mid-2000s and carries the widest language database of the three — the usual pick when a tree contains less common languages. Its signature extra is cloc --diff, which counts what changed between two directories, archives, or git revisions — useful for release reports. Trade-off: being Perl, it is the slowest of the three on very large trees, though fine on typical repositories.

scc

scc counts like the other two but reports more: per-file cyclical complexity, COCOMO effort and cost projections, license detection, and byte estimates, across a wide range of output formats. If your report needs "how big and how tangled," scc produces both in one pass. The extras come with a caveat: complexity-based figures are estimates by construction and won't match tokei/cloc line totals used as a baseline — the OctoCounts vs scc page has details.

Which is faster: tokei, cloc, or scc?

On very large trees, the Rust and Go implementations are dramatically faster than Perl-based cloc — that much is consistent with each project's own published claims. Between tokei and scc, the gap is usually small and flips with the file mix and hardware. Absolute numbers vary too much to crown one winner here: if the difference matters for your CI budget, run two of them on the same checkout and keep the faster. (For reference points measured over a network, OctoCounts' pilot study published per-request timings of archive-based tokei analysis on react and vite.)

Do tokei, cloc, and scc give the same numbers?

Rarely, exactly. Each tool ships its own language database, its own comment-syntax rules, and its own defaults for skipping directories, so totals can differ by a few percent on the same checkout. That is normal and is exactly why a citation should name the tool and version: “32,360,324 code lines by tokei at commit 4056b3c9d3c9” is reproducible; a bare “32 million” is not. The SLOC glossary defines the categories the three tools share.

Can I run tokei without installing it?

Yes — OctoCounts runs tokei server-side on public GitHub repositories: paste a URL and get the same counts the CLI would produce, pinned to an exact commit, with shareable report pages, README badges, and a JSON API. For private repositories, install the CLI; the tokei online guide explains when each route fits.

Bottom line: for local counting the three tools overlap far more than they differ — pick by extras (scc), language coverage and diffing (cloc), or Rust speed and clean output (tokei). When the tree is a public GitHub repository and the goal is a number you can share and cite, running tokei online through OctoCounts skips the install and pins the result to a commit.

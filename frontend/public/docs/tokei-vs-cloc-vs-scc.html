tokei vs cloc vs scc: which line counter?

tokei, cloc, and scc are three open-source line counters, and all three split a local source tree into code, comment, and blank lines. The differences: tokei (Rust) is built for fast counting with compact output; cloc (Perl) has a long history and a diff mode; scc (Go) adds cyclomatic complexity estimates, COCOMO effort projections, and license detection on top of the counts.

All three run on Linux, macOS, and Windows, and all three read a local checkout — none of them talks to a hosted repository by URL.

tokei

tokei is the counter to reach for when the job is "count this tree, fast, without ceremony." Output is a compact per-language table; --output json emits machine-readable totals via serde, and a tokei.toml can carry a shared configuration. It supports 200+ languages and is the engine OctoCounts runs server-side — the OctoCounts vs tokei page covers the split of labor between the CLI and the web service.

cloc

cloc has been counting trees since the mid-2000s and supports many languages — the usual pick when a tree contains less common languages. Its signature extra is cloc --diff, which counts what changed between two directories, archives, or git revisions — useful for release reports. Measure execution time on your own source tree with pinned tool versions if speed matters.

scc

scc counts like the other two but reports more: per-file cyclomatic complexity, COCOMO effort and cost projections, license detection, and byte estimates, across a wide range of output formats. If your report needs "how big and how tangled," scc produces both in one pass. The extras come with a caveat: complexity figures are estimates and measure something different from code-line totals; compare line counts separately under matching rules — the OctoCounts vs scc page has details.

Which is faster: tokei, cloc, or scc?

This page does not publish a controlled speed benchmark. If execution time matters, measure each tool on the same checkout, with pinned versions, equivalent exclusions, the same machine, and a stated cache state; keep the commands and results with your comparison. (For reference points measured over a network, OctoCounts' pilot study published per-request timings of archive-based tokei analysis on react and vite.)

Do tokei, cloc, and scc give the same numbers?

Not necessarily. Tools use different language definitions, comment parsing, and exclusion defaults, so totals can differ on the same checkout. No universal percentage difference follows from those implementation differences. For a verifiable citation, record the tool and version, exact source tree and commit, effective counting rules, and measurement date. Complexity estimates are separate metrics from line counts.

Can I run tokei without installing it?

Yes — OctoCounts runs tokei server-side on public GitHub repositories: paste a URL and get counts reproducible with the same source tree, tokei version, and effective filtering rules, pinned to an exact commit, with shareable report pages, README badges, and a JSON API. For private repositories, install the CLI; the tokei online guide explains when each route fits.

Bottom line: for local counting the three tools overlap far more than they differ — pick by extras (scc), language coverage and diffing (cloc), or Rust speed and clean output (tokei). When the tree is a public GitHub repository and the goal is a number you can share and cite, running tokei online through OctoCounts skips the install and pins the result to a commit.

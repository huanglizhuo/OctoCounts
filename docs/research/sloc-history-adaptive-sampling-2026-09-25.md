# SLOC 历史自适应采样设计(规划稿,2026-09-25)

状态:**Phase 0–2 已实现(2026-09-25,未提交)**;L2 形状细化与 L3 活跃度加权按计划
暂缓(Phase 3)。实现记录见文末"实现落地"一节。

## 1. 现状与成本模型

数据链路:`RepoHistoryChart.tsx` → `/api/seo/repo-history` → `repo_history.rs::run_sloc_backfill`
→ 每个采样点 = 1× `resolve_commit_before`(REST)+ `coordinator.submit`(ref 解析 +
报告缓存查询;未命中则 = codeload 归档下载 + tokei 扫描 + DB 写入)。

每个采样点的真实成本构成:

| 成本项 | 量级 | 备注 |
|---|---|---|
| GitHub API 调用 | 1–3 次/点 | commits?until=1 次;ref 解析 GraphQL 1 次或 REST 2 次(有 ref_cache) |
| 归档下载 | ≈ 仓库当时体积/点 | 最大头;报告缓存命中则完全省掉 |
| tokei 扫描 | ≈ 文件数/点 | CPU;受 analyzer 信号量约束 |
| 回填墙钟时间 | 串行累加 | `await_job` 逐点等待,320s 超时/点 |

关键观察:

1. **采样数今天并不随历史增长**(cap 12),真正随时间增长的压力来自三处:
   归档体积随仓库变大;修"冻结 bug"后若做朴素每日前向采样,watched repos ×
   每日分析无上界;为观感提高 cap 时成本线性上涨。
2. **SLOC 只在 commit 处变化**。采样区间内无 commit 时,相邻点解析出同一 SHA,
   归档/扫描是纯浪费(等距日期采样对低活跃期repo系统性浪费)。
3. 图表渲染按真实日期投影(`RepoHistoryChart.tsx::project`),**不等距采样渲染完全正确**,
   这是自适应间隔可行的前提。

## 2. UI 侧约束(从图表几何推导)

- 画布 640×220,plox 区 576×164px。12 点时间距 52px;**24–36 点(16–24px 间距)是
  悬停交互与视觉密度的甜点区**;>60 点悬停开始难选,<10 点显得空。
- 人眼对折线偏差的感知阈值 ≈ 2px ≈ **绘图区高度的 1.2%**。这就是"不影响观感"
  的可量化定义:采样策略只需保证渲染出的折线与真实曲线偏差 < ~2px 等效值。
- 折线图形状保真标准做法是误差界下采样(Douglas-Peucker / LTTB / M4),
  监控系统的经典做法是**分层保留 + 老化降精度**(RRD/Prometheus 式)。
  两者组合即本方案。
- 注意:当前是全历史线性时间轴,近期加密采样在全历史视图里只占很小宽度——
  近期密度的收益主要在悬停读数和"仍在增长"的感知;**保护观感的根本是误差界,
  不是近期偏置**(若未来加缩放,近期分层立即兑付更多价值)。

## 3. 设计:四层,各自独立可上线

### L0 卫生层(纯减法,先做)

1. **SHA 去重**:`resolve_commit_before` 返回的 SHA 与上一点相同 → 跳过分析提交,
   不写快照(平台期只需首末两个锚点;SHA 变化时左锚已存在,最终点必写)。
   低活跃 repo 与久远区间直接免掉归档下载。
2. **端点锚定**:首点=首个 commit、末点=回填时刻的 HEAD(顺带改善"末点不是当前值"
   的观感问题)。
3. **批量解析**:GraphQL aliases 可把 N 个 `until` 查询合并为 1 次请求,API 配额省 N-1。

### L1 分层时间表 + 总预算(替代固定等距 12 点)

候选点按仓库年龄分层生成,再被总预算约束:

| 段龄 | 间隔 |
|---|---|
| ≤ 14d | 每日 |
| ≤ 90d | 每 2 天 |
| ≤ 1y | 每周 |
| ≤ 3y | 每两周 |
| > 3y | 每季度 |

- 总预算 `SLOC_HISTORY_MAX_POINTS`(建议默认 24,上限 40;保留旧
  `SLOC_HISTORY_MAX_SAMPLES` 作为回退兼容)。
- 超预算时从最老段开始丢弃"视觉显著性"最小的点(到邻点弦的垂直距离最小者),
   而非均匀抽稀。
- 效果:年轻 repo 近期更细腻(现在 12 点在 13 天仓库里已是每日,行为不变);
  老 repo 久远段自动稀疏,点数不随年龄膨胀。

### L2 形状保真细化(v2,可选)

- 粗扫(L0+L1 完成后)得到基线折线;对相邻点 |Δy| > 5% 全量程(或 Δx > 3×
  中位间距且 |Δy| > 2%)的段做二分细化(Douglas-Peucker 递归),预算内封顶。
- 保证:渲染折线与真实曲线偏差有界,重写/删库类尖峰不丢;平滑单调段不多花一个点。
- 每次细化 = 1 次解析 + 1 次缓存优先的分析,成本仍被 N_max 封顶。

### L3 活跃度加权(v3,可选)

- 1 次额外调用 `code_frequency`/`commit_activity`(注意 stats API 可能返回 202
  惰性计算、仅周粒度),把近一年的采样密度按 commit 密度加权;仅作布点参考,
  数值仍走 tokei 管线保持与主报告口径一致。
- 明确否决的替代方案:直接用 code_frequency 累加生成曲线(零归档成本)——
  它统计 diff 行数,与 tokei 的"代码行"口径不同(排除 dist/生成文件),
  会导致曲线终值 ≠ 页面主数字(39,948),破坏自洽。

### 与"冻结 bug"修复的耦合(前置)

当前一次性回填(`sloc_backfill_started_at IS NULL` 抢占)不修,以上只是静态优化。
配套改为:

- **前向增量**:对已完成回填的 watched repos 每日采样一次,但**HEAD SHA 未变则
  跳过分析**(1 次轻量 API 调用门控,把每日成本限制在"真正有提交的 repo"上)。
- **回填可续跑**:预算/墙钟(如 10 分钟)耗尽时标记 partial,下次访问从最后
  采样日期续跑,而非一次性全有全无。
- **老化压缩**:夜间任务对既有快照降精度——>30 天的保留每周桶的
  first/last/min/max(M4),>1 年保留每月桶;幂等执行。这是点数不随时间无界增长
  的保证,也是本设计"自动调整间隔"的运行期形态。
- 快照表可加 `source` 列(backfill/forward/compacted)便于观测,非必需。

## 4. 全局护栏与度量

- 每仓库每次回填:点数预算 + 墙钟预算 + 归档字节预算,任一耗尽即停(标记可续跑)。
- 回填任务时间片化:逐点之间加间隔/随前端轮询分批推进(前端已有 5s 轮询协议),
  避免一个老仓库回填长时间占满 analyzer 信号量。
- `AnalysisSource::SlocBackfill` 已存在,可用来给回填类 job 更低的信号量优先级,
  避免挤压有机流量。
- 指标(/internal/stats):每 repo 采样数、报告缓存命中率、归档字节、回填时长、
  压缩后点数、SHA 跳过率。上线前后用这些数字验证收益,而非拍脑袋。

## 5. 实施顺序建议

1. **Phase 0**:冻结修复(前向增量 + 末点锚定 + 可续跑)——否则历史再准也会立刻过期。
2. **Phase 1**:L0 + L1(SHA 去重、分层时间表、MAX_POINTS、预算护栏),纯配置驱动,
   无 schema 变更,风险最低。
3. **Phase 2**:老化压缩任务 + source 列。
4. **Phase 3**:L2 形状细化;L3 视指标决定是否需要。

各阶段独立可回滚(配置开关),Phase 1 预期把典型老仓库的回填分析次数从
12 次满配降到 6–8 次(SHA 去重 + 久远段抽稀),同时图表点数从 12 升到 ~24,
观感更密而非更疏。

## 6. 待确认问题

- 压缩任务删点还是标记弃用(留观测余地 vs 表更小)——建议先软删。
- 前向采样与 star 快照任务合并为一个调度循环,还是独立(建议独立,失败域隔离)。
- 图表 UI 是否同步加"采样点"小圆点(>20 点时辅助悬停),属独立小改动。

## 7. 实现落地(2026-09-25)

Phase 0–2 全部落地于 backend(`github.rs` / `repo_history.rs` / `store.rs` /
`config.rs` / `api.rs` / `main.rs` / `golden.rs`),`cargo test` 194 通过:

**Phase 0 — 冻结修复**
- 回填可续跑:`start_sloc_backfill_if_needed` 增加冷却重占(未完成且
  `started_at` 距今超过 reclaim 窗口即可重占);`run_sloc_backfill` 返回
  是否走完日程,预算耗尽/失败都不再标记完成,重跑经报告缓存近乎零成本。
- 前向增量:`spawn_sloc_forward_task`(独立于 star 任务)周期扫描已完成
  回填的 watched repos,HEAD SHA 与最新快照一致则只花一次轻量 ref 解析,
  变化才跑一次分析并 upsert 今日快照(`source='forward'`)。
- 末点锚定:回填日程最后一点恒为 `now`,平台期也强制记录当日值。

**Phase 1 — L0 + L1**
- 分层时间表:`sample_dates_tiered` 取代等距 `sample_dates`
  (14d/1d、90d/2d、365d/7d、3y/14d、更久 91d);超预算先稀释老段
  (old_multiplier 倍增),仅当近期窗口本身放不下才动 recent 段。
- SHA 去重:相邻采样解析出同一 commit 即跳过分析(平台期只留边界)。
- 批量解析:`resolve_commits_before` 用 GraphQL aliases 把 N 次
  `until` 查询合并为 1 次(有 token 时;无 token 或任何失败逐条回退 REST)。
- 预算护栏:总点数(`SLOC_HISTORY_MAX_POINTS`,默认 24,旧变量名仍作
  回退默认)+ 墙钟(`SLOC_BACKFILL_WALL_CLOCK_SECONDS`,默认 600s)。
  归档字节沿用既有单次上限,未做累计预算(分析器信号量天然限流)。

**Phase 2 — 老化压缩**
- `sloc_snapshots` 内联迁移新增 `source`('backfill'/'forward')与
  `superseded_at`(软删);重写同日期快照自动复活。
- `spawn_sloc_compaction_task` 每日:`compaction_keep_dates` 纯函数按
  ">30 天周桶 / >1 年月桶,桶内留 first/last/min/max(M4)"计算保留集,
  其余软删;最新点永不压缩;≤8 点的历史不动。

**与设计的偏差(有意为之)**
- 前向采样与压缩独立成任务,未合并进 star 快照循环(失败域隔离,同 §6 建议)。
- 软删而非物理删除(§6 开放问题按建议取软删)。
- 归档字节累计预算未实现(见上)。
- 图表 UI 采样点圆点未加(独立小改动,待定)。
- 未接入 /internal/stats 指标(任务内有 tracing::info 计数日志)。

**上线注意**
- 既有 repo(如 huanglizhuo/OctoCounts 的 09-05 冻结序列)在部署后由前向
  采样任务自动补当日点;两点之间出现的缺口属预期(不会再全量重扫)。
- 冷却窗口在 config 内被钳制为 > 墙钟预算 + 60s,防止运行中回填被双占。

**部署后追加(v0.7.17 / v0.7.18,2026-09-25)**
- v0.7.16 生产验证发现两处健壮性缺口 → v0.7.17:部分成功(0 < recorded <
  resolvable)的回填不再标记完成,走冷却续跑;全败(recorded=0)仍完成以避免
  系统性失败(如超大归档)被无限重试,由前向任务按日治愈;前向任务对"无快照"
  仓库照常采样 HEAD(原实现直接跳过);每样本失败与运行摘要均落日志。
- v0.7.17 验证又暴露批量解析的**别名解析 bug**:`aN: history(...)` 的别名即
  字段本身,响应中没有 "history" 包裹层,原解析多跳一层导致全部返回 null、
  且形状完好不触发 REST 回退 → 所有新回填 resolvable=0。v0.7.18 修复并经
  本地复现 + 生产验证(agent-monitor 新回填 recorded=1)。
- 已知运营噪音:前向遍历对已删除/私有仓库每轮各花 10-20s(仅告警跳过),
  大列表时一轮较慢;后续可加按仓库的失败退避。sub-day 新仓库首日只有一个
  采样点,图表需等第二个点(次日前向采样)才渲染。
